# v1.11.3 — 边生成边排版

> 发布日期：2026-11-26 · versionCode 23 · 需要 Android 8.0（API 26）以上

## 一句话

流式生成时不再显示 Markdown 原文，标题、列表、代码块、表格都是边写边长出来的。

## 之前是什么样

流式期间整段走纯文本分支，等 `isStreaming` 变 false 才切到 Markdown。所以三千字的回答，
你前 90% 的时间看到的是这样：

````
## 主要问题

当前实现有三个问题：

1. **流式解析只取 content**，推理模型的思考被丢掉
2. 上下文**没有压缩**，长对话必然撞上后端长度上限

```kotlin
val spans = MarkdownParser.parseInline(text, refs)
```
````

读起来像在读源码，回答写完的瞬间又「啪」地变成排版好的样子，整段高度还会重排一次。

## 现在

同一时刻，正在生成的内容已经是排版后的：

- `##` 立即变成标题
- `**粗体**` 立即变粗
- ` ``` ` 一出现就是代码块，即使还没收到结束围栏 —— 闭合时不会跳
- 表格在分隔行 `|---|` 到达的瞬间变成表格，之后逐行长出

## 为什么不是「每个 token 都重渲染」

解析是 O(n) 正则扫描，DeepSeek 这类后端 20~50 token/s，长回答上每个 token 全量重排
会明显掉帧。改成 **90ms 采样**（约 11fps），观感上仍是连续打字，解析次数少一个数量级。

实测数据（解析器原样编成 JVM 跑）：

| 文本长度 | 单次解析 | 11fps 下的 CPU 占比 |
|---|---|---|
| 489 字 | < 1ms | 约 1% |
| 3,509 字 | 0.83ms | 约 0.9% |

采样用的是「固定间隔推最新值」，不是「变化后等 90ms」。后者有个陷阱：每个新 token
都会重置计时器，如果 token 间隔一直小于 90ms，就永远等不到触发 —— 表现成攒一大段
再突然吐出来，比不节流更跳。

另外测了结构稳定性：把一段典型回答逐 3 字符追加，每一步都解析一次，块数量最大跌幅只有 1
（那一次是 `[ref]: url` 引用定义行从「临时当段落」变成「被识别并跳过」，属于正确行为）。
没有出现「某一行未闭合导致整段塌缩成代码块」的情况。

## 顺手修了滚动的三个问题

做实时渲染时发现的，不修的话新功能会放大它们：

**① 视图被反复拽回长回答的开头**

原来每次文本变化都调 `animateScrollToItem(messages.lastIndex)`，而这个 API 是把该 item
的**顶部**对齐视口顶部。回答一旦超过一屏，每追加一段就把视图拉回它的第一行 ——
用户永远看不到正在生成的那段。

现在滚到列表末尾的 1dp 哨兵：LazyColumn 不能滚过内容末尾，会自然 clamp 到底部，
短消息和长消息都能正确落位。

**② 有压缩提示条时滚错位置**

`messages.lastIndex` 被直接当作 LazyColumn 的 item index，但压缩提示条也是一个 item，
于是每次都滚到倒数第二条消息。现在把前缀 item 算进去了。

**③ 每个 token 启动一次滚动动画**

新旧 `animateScrollToItem` 互相打断，观感像抽搐。改为 120ms 采样，流式期间用无动画的
`scrollToItem`。

## 新增：往上翻时暂停跟随

靠 `lastScrolledBackward` 判断滚动方向：用户主动上滑就停止自动滚动，滑回底部或点
「回到最新」恢复；自己发消息时也自动恢复（发出去就是为了看回复）。

没有这个判断的话，流式期间每 120ms 一次「滚到底」等于不让人读上文。

## 已知限制

- 行内标记（`**`、`` ` ``）在闭合前的那一瞬间会显示为字面字符。这是 Markdown 的固有
  行为，只能靠模型少跨行加粗来缓解。
- 表格在分隔行到达前会先以「带竖线的段落」出现 100ms 左右，然后变成表格 —— 会有一次
  高度跳变。
- 90ms 采样意味着最后一个字符可能在流结束后 90ms 才出现；流式结束时直接取全文，
  实际感知不到。
